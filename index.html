Deploying a Zero-Downtime Kubernetes Cluster on Google Cloud from Nairobi's iHub

We walked through the entire setup live at iHub last month — from cluster bootstrapping to rolling updates — and documented every step for the Kenyan developer community building on GKE.

JM
James Mwangi
Staff Engineer · iHub Labs
Feb 28, 2025 · 14 min read · 2,840 views DevOps GCP
"Resilience by design,
from Nairobi to the cloud."

Overview

Last month's iHub workshop brought together 60+ Kenyan engineers for a hands-on walkthrough of standing up a production-grade GKE cluster using Google Cloud's africa-south1 region — the closest GCP data centre to East Africa. In this guide, we document every command and config file we used.

We chose e2-standard-4 instances for the initial node pool, giving us 4 vCPUs and 16 GB RAM per node at reasonable cost within Kenya's typical startup budget constraints. You can scale this up as your traffic grows.

Prerequisites

  • A Google Cloud project with billing enabled
  • The gcloud CLI installed and authenticated
  • kubectl version 1.28 or later
  • Basic familiarity with Docker and container concepts

Cluster Setup

Begin by enabling the GKE API and setting your project defaults. We use the africa-south1 region throughout for latency and data-residency reasons relevant to Kenyan and East African deployments.

bootstrap.sh 
#!/bin/bash
# Bash n Build · GKE Zero-Downtime Bootstrap

gcloud config set project YOUR_PROJECT_ID
gcloud services enable container.googleapis.com

gcloud container clusters create bash-n-build-prod \
  --zone=africa-south1-a \
  --num-nodes=3 \
  --machine-type=e2-standard-4 \
  --enable-autoscaling \
  --min-nodes=2 --max-nodes=8 \
  --enable-autorepair \
  --enable-autoupgrade

gcloud container clusters get-credentials bash-n-build-prod \
  --zone=africa-south1-a

Rolling Deployments

Kubernetes rolling updates allow you to deploy new versions with zero downtime by incrementally replacing Pods. The key configuration is setting maxSurge and maxUnavailable in your Deployment spec:

Zero-Downtime Config

Set maxUnavailable: 0 to ensure no Pods are terminated until replacements are healthy. Combine this with proper readiness probes on your FastAPI service for a bulletproof deployment pipeline that would work well with a Bash n Build API backend.
